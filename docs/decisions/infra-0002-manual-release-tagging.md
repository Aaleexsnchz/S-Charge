# infra-0002: Tag releases by hand; derive the running version from the tag

**Decision.** Releases are **tagged manually** with a deliberately chosen semantic version. The running version is **derived from the git tag** — `git describe --tags` feeds an `APP_VERSION` build arg at image build time, surfacing in `/api/health` and on the profile screen. No version string is maintained in `backend/pyproject.toml`, `frontend/package.json` or anywhere else. No release-automation bot.

Bump rules: a **minor** marks a phase or a meaningful feature set shipping; a **patch** marks fixes on top. `v0.1.0` is the first successful production deploy — release history starts at deployment, not retroactively at Phase 1. **`v1.0.0` is the build presented for the thesis.**

**Rationale.** The version number here is a statement about scope aimed at a reader of the thesis: it should be able to say "this is the phase that shipped private points". Deriving it from commit types produces a number that answers a different question — how many `feat:` commits landed. Between tags, `git describe` reads `v0.1.0-3-gabc1234`, so production always states how far ahead of the last release it is without anything being kept in sync by hand.

**Consequences.**

- Cutting a release is a manual act of judgement, and can therefore be forgotten. Accepted: at ~10–20 releases over this project's life, that is cheaper than the automation.
- **There is no `CHANGELOG.md`.** Release notes are generated by GitHub from merged PR titles, which makes PR titles the user-visible record and gives the Conventional Commits rule a second purpose. [git-cliff](https://git-cliff.org) can render a changelog from existing history on demand if the thesis ever wants an appendix — parked in [ideas-backlog.md](../ideas-backlog.md).
- Images must be built where the git history is available; a build from a tarball without tags produces an unstamped version.
- The deploy pipeline must `git fetch --tags` before building, or production reports a stale version.

**Rejected alternatives.**

- *`release-please`.* Chosen first, then reversed on reading its model. It derives the bump from commit types, which fights a scheme where the number is a deliberate statement — steering it means `Release-As:` footers on commits, more ceremony than tagging by hand. Its main value, keeping version strings in sync across manifests and the UI, evaporates entirely once the version comes from the tag. Against that it needs a repository setting allowing Actions to open pull requests, adds a bot-authored PR per release, and PRs it opens with `GITHUB_TOKEN` do not trigger CI — so release PRs would be the only unchecked ones in a repository whose whole point is that `main` is always deployable.
- *`semantic-release`.* Tags on every qualifying push with no human gate. Wrong for a repository where merging to `main` deploys to production.
- *`changesets`.* Built for versioning published JavaScript packages in a monorepo. This project publishes nothing.
- *A hand-maintained version string in the manifests.* The thing every option above exists to avoid; guarantees drift between three files and the UI.
