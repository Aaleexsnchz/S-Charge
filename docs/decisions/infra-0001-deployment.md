# infra-0001: Deploy the Docker Compose stack on a single small VPS behind Caddy


**Decision.** Run the existing `docker compose` stack on **one small always-on Linux VPS**. [Caddy](https://caddyserver.com/) terminates TLS with automatic Let's Encrypt certificates and serves the frontend and `/api/*` from a **single origin**. The REVE/PVPC refresh ETL runs from a `scheduler` container inside the stack, independent of any laptop. CI/CD is GitHub Actions: the test matrix gates every push, and a **successful** CI run on `main` triggers an SSH deploy (`git pull` → `docker compose up -d --build` → `alembic upgrade head`). Host: **Hetzner**, a 2 vCPU / 4 GB x86-64 instance in an EU region.

**Rationale.** Constraints: 1–2 users (just me at first, a couple at the live demo), minimal spend, must be secure, must keep the refresh ETL running with my laptop closed, and must give a real HTTPS URL openable on a phone. A single VPS is the tightest fit:

- *Same artifact, built from this repo.* The app is a `docker compose` stack (Postgres, backend, frontend, Caddy, scheduler). A VPS runs it unchanged — no re-platforming, no serverless rewrite, no splitting the stack. Development runs the backend and frontend natively against a containerised Postgres, so dev is deliberately *not* the deployed artifact; the prod stack is instead verified by `just prod-up` locally and by CI building all three prod images on every pull request.
- *Makes the ETL laptop-independent.* The biggest practical reason to deploy: `refresh_reve.py` and the PVPC ingest move to a host that is on 24/7, so the catalogue stays fresh without my machine awake. (Today they run from the laptop's cron — see [thesis/planificacion-de-siembra.md](../thesis/planificacion-de-siembra.md).)
- *Same-origin keeps the session model simple and safe.* Auth is a single HttpOnly cookie ([auth-0002](auth-0002-cookie-session.md)). Serving the SPA and the API from one domain behind one proxy avoids `SameSite=None` cross-site cookies and broad CORS — fewer moving parts and a smaller attack surface than a split frontend/backend.
- *HTTPS is required anyway.* The PWA ([fe-0002](fe-0002-pwa.md)) and browser geolocation both need a secure context; Caddy provides and auto-renews certificates with near-zero config.
- *Cost is ~€7–18/mo*, with no per-service multiplication and no free-tier sleeping.

**Implementation (Phase 5).** Slice-by-slice plan: [phases/phase-5.md](../phases/phase-5.md). Host runbook: [setup/deployment.md](../setup/deployment.md).

- **Host spec** (the actual requirement; the SKU is a purchasing detail): **2 vCPU · 4 GB RAM · x86-64 · ≥40 GB disk · EU region · Ubuntu 24.04 LTS · monthly billing · SSH key attached at creation.** 4 GB is a floor because the deploy builds the prod images on the host (`up -d --build`) and 2 GB does not survive a Vite production build next to Postgres, backend and Caddy. x86-64 rules out every ARM option (Oracle Always-Free, Hetzner CAX, Scaleway ARM) until an arm64 supercronic binary lands in [backend/Dockerfile](../../backend/Dockerfile).
- **Provider: Hetzner** — [CX23](https://www.hetzner.com/cloud/cost-optimized/) (~€7/mo) when in stock, else [CPX22](https://www.hetzner.com/cloud/regular-performance) (~€12–18); CX stock is per location, FSN/NBG/HEL are separate pools. Both bill hourly with no minimum term and no setup fee, so a wrong-sized box costs cents to discard. Fallbacks if Hetzner is unusable, best first: [netcup](https://www.netcup.com/en/server/vps) (~€4–7), [IONOS](https://www.ionos.com/servers/vps) (~€5–10), [OVHcloud](https://www.ovhcloud.com/en/vps/) (~€6–12), [Scaleway](https://www.scaleway.com/en/cost-optimized-instances/) x86 (~€7–12) — cheaper on paper, paid for in contract terms or annual prepay. Prices indicative, checked 2026-07-27.
- **Domain:** a registered domain from a cheap registrar (~€10/yr); optional Cloudflare (free) for DNS.
- **Reverse proxy:** Caddy in the compose — `:443` serves the frontend static build and proxies `/api/*` to the backend; automatic TLS + HTTP→HTTPS redirect + HSTS.
- **`docker-compose.prod.yml` is a standalone file, not an override.** It builds the frontend and backend `prod` targets, **does not publish `5432`** so Postgres is reachable only on the internal network, and injects secrets from a server-side `.env` (never committed). Standalone because Compose merging *appends* to `ports:` rather than replacing it, so an override cannot cleanly unpublish `5432` without recent-Compose `!reset` tags; a separate project name also lets the prod stack be smoke-tested next to the dev stack locally.
- **Scheduler:** a `scheduler` service built from a Docker stage extending the backend `prod` image with a pinned [supercronic](https://github.com/aptible/supercronic) binary and a repo-committed [crontab](../../backend/crontab). It invokes `python -m scripts.refresh_reve` and the PVPC ingest **directly inside the container** and logs to **stdout**, so ETL output rides the container log stream (`docker compose logs -f scheduler`) with the platform's logging driver handling rotation. No host crontab to provision — the stack stays self-contained and portable. Host-level ops scripts (DB backup) still live on the host, per [operations.md](../operations.md).
- **CI/CD:** [ci.yml](../../.github/workflows/ci.yml) gates every push and additionally builds the three prod image targets, so a broken Dockerfile fails in CI rather than on the server at deploy time. [cd.yml](../../.github/workflows/cd.yml) triggers on `workflow_run` — a **successful** CI run on `main`, not the push itself, which would race the tests. GitHub Secrets hold the SSH key and deploy config.
- **Branch protection:** `main` is PR-required (GitHub Flow), no direct commits, no force-push. `main` is what production runs.
- **Releases:** tag `vMAJOR.MINOR.PATCH` **by hand**; the running version comes from `git describe --tags` via an `APP_VERSION` build arg, surfaced in `/api/health` and on the profile screen. `v0.1.0` = first production deploy; **`v1.0.0` = the evaluated build**. Operating rule: [AGENTS.md](../../AGENTS.md) → Releases.

**Pre-deploy security gate** (must pass before first public exposure; run `/security-review`):

- HTTPS + HSTS; HTTP→HTTPS redirect.
- Host firewall: only 80/443 + SSH; SSH key-only, root login disabled, fail2ban.
- Postgres not published to the host; strong DB password; backups confirmed (Backblaze B2 already configured).
- Secrets server-side only; dev secrets rotated; Google OAuth redirect URI + Resend sender set for the prod origin.
- Cookie `Secure` + `SameSite=Lax`; CORS locked to the one origin; auth rate limits kept.
- Optionally keep registration invite-only during the demo (email verification already blocks drive-by signups).

**Rejected alternatives.**

- *Vercel (frontend) + a separate backend.* Vercel is excellent for static/SPA hosting (global CDN, free TLS, preview deploys) and could host the Vite build for free. But it is serverless / front-end-oriented: it does not run a long-lived FastAPI process, Postgres, or a rate-limited multi-hour ETL well (function time limits, cold starts; Vercel Cron is coarse and time-boxed). Using it forces a split origin (`SameSite=None` + CORS) and still leaves the backend, database and cron to host elsewhere — more parts, more attack surface, no demo-visible gain at this scale. It *is* a sensible scale-up path for the frontend (noted in the scaling chapter).
- *Supabase (managed Postgres / BaaS).* Tempting to offload Postgres. But the free tier **pauses the project after ~a week of inactivity** (fatal for an always-on demo + cron) and caps at 500 MB; Pro is $25/mo (beyond "minimal"). I already have a working, thesis-documented auth stack ([auth-0001](auth-0001-fastapi-users.md)/[auth-0002](auth-0002-cookie-session.md)) and an Alembic-managed schema, so Supabase Auth / edge functions would mean rewriting a *pillar* of the thesis for no benefit. At most I'd use its bare Postgres — which I already run for free in Compose with backups.
- *Container PaaS — Render / Railway / Fly.io.* The closest managed option. Render's free web service **sleeps** on idle and its free Postgres **expires after 90 days**; Railway is usage-based past a small credit; Fly.io fits Docker + volumes + scheduled machines but its free allowances shrank and its managed-Postgres story is in flux. For this stack a single VPS is cheaper and simpler, and sleeping instances break both the PWA demo and the ETL. Fly is the strongest runner-up if managed infra is wanted later.
- *Big-cloud (AWS/GCP/Azure) or managed Kubernetes / ECS.* Trials then real bills, plus orchestration overhead that is pure overkill for 1–2 users. GCP was reconsidered mid-phase and rejected concretely: its Always-Free tier is a 1 GB `e2-micro` restricted to US regions — too small to build images on-host and it forfeits the EU data-locality argument — while anything workable bills at roughly 3x Hetzner. Belongs in the scaling chapter as the theoretical growth path.
- *Podman instead of Docker on the server.* Rootless and daemonless by default, with systemd integration through Quadlet — a genuinely better security posture in the abstract. It loses here on fit rather than merit. `podman compose` is a shim that delegates to an external compose implementation, and this stack leans on exactly the parts where that shim is thinnest: healthchecks, `depends_on: condition: service_healthy`, and multi-stage build targets. Rootless containers also cannot bind 80/443 without tuning `net.ipv4.ip_unprivileged_port_start`, and Ubuntu 24.04 ships Docker Engine as a first-class apt repository, which is what the runbook documents. The security gap it would close is largely closed already by other means: the backend prod image runs as a non-root `appuser`, Postgres publishes no port, and `ufw` limits the host to 22/80/443. Podman's payoff shows up in fleets and systemd-managed hosts — revisit it if this ever becomes more than one VPS running one stack.
- *Split static-CDN frontend + VPS API (Cloudflare Pages / Netlify + VPS).* Genuinely free, fast frontend, but reintroduces cross-origin cookie/CORS complexity for no benefit at demo scale. Revisit only when CDN edge-caching actually matters.
- *Oracle Cloud Always-Free (ARM Ampere, €0) and other ARM hosts.* The zero-cost option, blocked by the x86-64 requirement above: supercronic and both prod images would need arm64 builds first. Worth revisiting only if the spend ever has to reach zero.
- *A free DuckDNS subdomain instead of a registered domain.* `duckdns.org` is on the Public Suffix List, so Google treats the subdomain as the top private domain and expects ownership verification before accepting it as an OAuth authorised domain. ~€10/yr removes that from the critical path and reads better at the defense.
- *Host cron or a systemd timer for the ETL.* The job would run via `docker compose exec`, whose output attaches to the host caller rather than the container: ETL logs never reach `docker compose logs` and instead accumulate in an unrotated host file that grows unbounded, separate from the app's own logs. It also means a host crontab to provision on every future host. Surfaced while investigating a REVE-side 504 regression where that host file was the only window into the cron's behaviour.
- *APScheduler instead of supercronic.* A Python scheduler entrypoint is code to write, test and keep alive; supercronic is a pinned binary plus a cron-syntax file already in the repo. The unused `apscheduler` dependency was dropped.
- *`release-please` for releases.* It derives the bump from commit types, which fights a versioning scheme where the number is a deliberate statement about scope ("this is Phase 6"); steering it needs `Release-As:` footers on commits. Its main value — syncing version strings across `pyproject.toml` / `package.json` / the UI — disappears entirely once the version comes from the tag. It also wants a repo setting allowing Actions to open PRs, and PRs it opens with `GITHUB_TOKEN` do not trigger CI, so release PRs would be the only unchecked ones. At ~10–20 releases over this project's life the automation never pays for itself. `semantic-release` (tags on every push, no gate) and `changesets` (built for publishing JS packages) fit worse still. [git-cliff](https://git-cliff.org) is parked as a changelog generator if the thesis wants an appendix.
