# auth-0004: Rate-limit the auth endpoints, and treat the audited client IP as personal data

> Slice 13 decision. Two problems that only exist once the app is reachable from the internet, plus the data-protection position the second one forces.

## Context

Both were found by reading the production artifacts against the [infra-0001](infra-0001-deployment.md) gate. Neither is a regression: neither has ever worked.

- **Nothing limits the auth endpoints.** Verification blocks drive-by *registration* ([auth-0003](auth-0003-preregistration-shell-mitigation.md)) but says nothing about attempts against accounts that already exist, and `/forgot-password` is an unmetered send-an-email endpoint for anyone who finds it.
- **The audited IP is the proxy's.** `UserManager` logs `request.client.host` on four auth events, and uvicorn trusts `X-Forwarded-*` only from `127.0.0.1` by default, so every event records Caddy's container address.

The order is not free: a limiter keyed on an IP that is always Caddy's puts the entire internet in one bucket, so the first attacker to hit the limit locks out every user. The proxy fix is a precondition for the limiter, not a companion to it.

## Decision

**Limit per IP and per path**, at the router mount points in `app/routers/auth.py`: 10/minute on the login router, 10/hour on registration, 5/hour on the two routers that send mail. Endpoints whose cost lands in somebody else's inbox get an hourly budget; the rest are protected against brute force, not expense.

**Trust the proxy narrowly**: `--forwarded-allow-ips=172.16.0.0/12` on the `prod` stage's uvicorn command — the compose network, where Caddy is the only thing that can reach a backend publishing no ports.

**Treat the resulting log lines as personal data**, on the legitimate-interest basis, with retention bounded by log rotation.

## Rationale

### `limits` directly, not `slowapi`

`slowapi` was declared in `backend/pyproject.toml` from the start and never imported. **It can do this job** — that was checked, not assumed. Its `@limiter.limit` decorator wants a function it can wrap before FastAPI builds the route, and every auth route here is generated by `fastapi-users`; the pattern the library's own discussion recommends is to reassign `route.endpoint` on the generated router and rely on `include_router` rebuilding the route from it. Measured against the real register router, that yields `[201, 400, 400, 429, 429]` at `3/minute`. It works.

It was still rejected, for one reason: **it fails silently.** The helper walks `router.routes` matching a library-internal path string, and a `fastapi-users` upgrade that renames `/forgot-password` makes the loop match nothing, decorate nothing, raise nothing, and leave the endpoint unlimited. A security control whose failure mode is "quietly off" is the wrong shape, and the published helper does not even return whether it matched. A router-level `dependencies=[...]` uses documented FastAPI API, names no paths, and a mistake there is an import or signature error at boot.

The cost of that is ~30 lines over `limits` — the engine `slowapi` itself uses, already in the tree as its dependency. `slowapi` is dropped and `limits` promoted to a direct one.

The second reason only bites later, and is the stronger one. **`slowapi` is synchronous**: it imports `limits`' sync storage and strategy APIs, never `limits.aio`, and nothing on its check path is a coroutine. Against in-memory counters that is a dict lookup and does not matter. Against Redis — the upgrade [production-readiness.md](../production-readiness.md) names as the fix for per-process counters — it is a blocking network round-trip inside an async endpoint, stalling the event loop on every request to a limited route. The storage backends and window strategies are `limits`' rather than `slowapi`'s, so going direct keeps all of them *and* awaits them; `storage_from_string("async+redis://…")` is the whole migration.

One difference that turns out **not** to exist, since it looked decisive and was measured: whether a blocked request still touches the database. It does not, under either approach. The session dependency resolves lazily and the connection is only made inside the endpoint body, so both the decorator and the dependency short-circuit ahead of it — verified against an unresolvable database host, where both return `429` without a connection attempt.

What is given up is real and small: `slowapi` would supply `X-RateLimit-*` response headers (only `Retry-After` is emitted here), an in-memory fallback for when Redis is unreachable, and thirty lines nobody on this project has to maintain.

### A CIDR, not `*`

`*` is not merely broader — it takes a **different value**. uvicorn's `_TrustedHosts` short-circuits on `always_trust` and returns the *leftmost* `X-Forwarded-For` entry; given a network match it instead walks the chain from the right and returns the first untrusted hop. On a header reading `1.2.3.4, 203.0.113.9` the two disagree:

| `--forwarded-allow-ips` | resolved client |
| --- | --- |
| `*` | `1.2.3.4` |
| `172.16.0.0/12` | `203.0.113.9` |

That difference is only latent today, because Caddy discards client-supplied `X-Forwarded-*` values unless `trusted_proxies` is configured — *"by default, the proxy will ignore their values from incoming requests, to prevent spoofing"*, and `trusted_proxies` (added in 2.6.3) is what makes it preserve and append them instead. Confirmed against `caddy:2.11-alpine`, which passes exactly one header instance holding the real peer however many the client sends. So `*` happens to be safe *given the current Caddyfile*, and stops being safe the moment a CDN goes in front and `trusted_proxies` appears. The CIDR costs the same to write and does not depend on a default in another component.

### Client IPs are personal data, and logging them is lawful

An IP identifies a person for anyone who could lawfully compel the subscriber's identity, so it is personal data under GDPR even when dynamic (*Breyer*, CJEU C-582/14). Logging it needs a lawful basis, and the one that applies is legitimate interest, Art. 6(1)(f) — Recital 49 names network and information security explicitly, which is what an auth audit trail and a rate-limit key are. This is the settled case rather than a grey area; the obligations it carries are disclosure, purpose limitation and a bounded retention, not consent.

Spanish law adds nothing here: the 12-month traffic-data retention in Ley 25/2007 binds electronic-communications operators and access providers, not a web application.

### Retention, and where the logs live

They stay on stdout, captured by Docker's `json-file` driver. Retention is bounded by rotation — `max-size: 10m`, `max-file: 3` per service in [docker-compose.prod.yml](../../docker-compose.prod.yml) — which by default was **unbounded**, so an unbounded personal-data store was also the disk-exhaustion risk nobody had capped.

This is honestly a partial measure: rotation bounds *volume*, and storage limitation asks for a bound in *time*. At this traffic a 30 MB window is months, not weeks. A time-based policy belongs with the rest of the GDPR work already recorded as unaddressed in [production-readiness.md](../production-readiness.md) — a published privacy policy, a lawful-basis statement, processor agreements, erasure and portability. The point of recording it here is that the retention question is now answered deliberately rather than by omission.

## Consequences

- The limiter's counters are **in-process**: per container, lost on restart, and correct only while the backend runs a single uvicorn worker. A second worker would give each its own counters and multiply every limit. This is the same single-instance assumption the scheduler already carries.
- **Counters do not survive a deploy.** A redeploy resets every window, which is a real if minor weakening during a rolling restart.
- **Limits are per IP, so NAT shares them.** An audience behind one office or conference network shares one login bucket; 10/minute is chosen to leave room for that, but a demo to a large room on shared wifi is the scenario that would first hurt.
- Limits are constants in code, so loosening one is a redeploy — and deploys are tag-driven ([infra-0003](infra-0003-deploy-on-tag.md)). Making them settings was rejected as premature; this is the cost if that turns out wrong.
- The four `auth` events now carry a real IP, which is what makes them useful and simultaneously what brings them in scope above.
- **Neither half is exercised by `just api`**, which serves uvicorn directly with no proxy in front. Both are still checkable without a server, by running the prod image behind a Caddy container on a Docker network — done, and the counters key on the client rather than the proxy. What that rig cannot show is behaviour against real public addresses.

## Rejected alternatives

- *`slowapi`, as originally planned.* Works, via the route-mutation pattern above; rejected for its silent failure mode, not for inability. Dropped from the dependencies rather than left declared and unused. Its `SlowAPIMiddleware` form is separately unusable here — it applies one default limit to every route in the app, which cannot express "mail endpoints get an hourly budget and nothing else is limited at all".
- *`fastapi-limiter`.* The dependency-shaped rate limiter, and the natural fit for `include_router` — but it is Redis-only. Adding a fourth service to the compose stack, to hold counters for one backend process, buys distributed correctness this deployment has no use for. It becomes the right answer the same day a second backend instance does.
- *Rate limiting at the proxy.* Where this often belongs, and nginx would have it built in (`limit_req`). Caddy does not: it needs the third-party `caddy-ratelimit` module and therefore an `xcaddy` build, replacing a stock image with a custom one. That is a real cost against an edge limiter that would also be blind to the distinction the limits here are built on — that `/forgot-password` is expensive and `/login` is not.
- *`--forwarded-allow-ips="*"`.* Correct only by virtue of Caddy's current default; see the table above.
- *`header_up X-Forwarded-For {remote_host}` in the Caddyfile.* Written first, then reverted: Caddy already does this, warns that the directive is redundant, and the warning is right. Kept as a comment naming the behaviour, since the safety of the whole chain rests on it.
- *An auth-events table in Postgres.* Queryable, backed up, and retention becomes a `DELETE` — but it puts a write in the auth path, needs a migration and a model, and pushes personal data into database backups whose retention is longer and coarser than the logs'. Worth revisiting only if login history becomes a *product* feature the user is shown, which is a different thing from a security log.
- *Shipping logs to object storage or a hosted aggregator (Loki, Better Stack, Axiom).* The right answer for a fleet: durable, searchable, retention set centrally. Here it adds a processor to the GDPR surface and an egress path for personal data, to serve one operator who can already `docker compose logs` on the one box. Revisit if a second host ever appears.
- *Limits as `Settings` fields.* Runtime tuning without a redeploy, at the cost of three more variables to keep in step with `.env.example`. Constants until a limit actually proves wrong.
